## 2. `httpx` is undeclared, and `openai` is the only reason it is there

`tests/test_fire_metrics_improvements.py` imports `httpx` at module
scope. It is not in `requirements.txt`; it arrives as a hard dependency
of `openai`, which is pinned `openai>=2.53.0,<3`.

That works today, and here is the exact position — read off the
container rather than recalled, because the version of this claim we had
written down was overstated:

```
openai 2.54.0
  base:            httpx<1,>=0.23.0          <- unconditional today
  extra httpx2:    httpx2<3,>=2.7.0, httpx<1,>=0.25.1
  extras offered:  aiohttp, bedrock, datalib, httpx2, realtime, voice-helpers
```

So `httpx` is currently a hard dependency of base `openai` and even the
`httpx2` extra keeps it — the import is not one release from breaking.
**What the `httpx2` extra tells you is the direction of travel**: they
are staging a migration, and the day `httpx` moves behind an extra or is
dropped, that module stops importing with no change on your side. When a
test file fails to import it goes quiet rather than red, which is the
part worth avoiding.

**We have now made the one-line fix** — `httpx>=0.28` in
`requirements.txt` — rather than leave it waiting on a reply. It is a
floor with no ceiling on purpose: `openai` pins what it needs and that
stays yours to decide, and a ceiling from us would only ever collide with
it. The line says nothing more than "we import this directly", which is
true and was true before.

*(And a correction to the aside this section used to carry. We wrote that
the 161-test difference between the local and deployed suites was a
curiosity to explain when reconciling counts. It was not a curiosity: it
meant 161 tests were not running locally at all, for weeks. The
diagnosis in this section was right the whole time and we filed it as an
explanation of a number instead of as a defect. Both packages are now
installed locally and both suites run the same 2,579 tests. If you ever
reconcile counts between the two, do it by unique test id — a line-grep
tally once produced a phantom 14-test discrepancy for us — and treat a
module-shaped difference as a module that is not executing.)*

## 4. The login bug your CRE test exposed was ours

Recorded properly in `docs/beckett-open-test-failures.md` §2, but the
mechanism is worth having directly because it will bite anyone who adds a
second `create_app()`.

`app.py` holds a **module-level** `login_manager = LoginManager()`, and
its `@login_manager.user_loader` closed over whichever app registered it
last. Your test called `create_app(TestConfig)`; from that point the
shared loader resolved users against `TestConfig` for the rest of the
process.

Measured rather than reasoned:

```
original app ADMIN_USERNAME: '<the real one>'
after create_app(TestConfig):
  user_loader replaced                             : True
  closure captures app  -> ADMIN_USERNAME          : 'test-admin'
  loading the real admin through the shared loader : None
  loading 'test-admin'                             : <models.User object>
```

That `None` is the entire failure: a later test sets `_user_id` to the
real admin, the loader says no such user, `@login_required` redirects,
and the assertion reads a login page. Alphabetical ordering meant your
module ran first and everything after it that needed a session was
exposed.

**Fixed in `5d1f393` — the loader reads `current_app` instead of a
captured app. Your test needed no change.** It was latent long before
your commit; yours is simply the first that made a second app.
